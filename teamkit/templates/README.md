# ひな形と書き方の手引き

TASK.md・報告・レポートのひな形と、その書き方。型の要求（なぜこの形か）は `teamkit/docs/taskmd.md` にあり、食い違うときはそちらが正。リポジトリごとの値（ポート、報告の写し先、持ち手の置き場所、作業の場所、一時の worktree、写しの置き場 など）は、導入したリポジトリの値の表 `.claude/teamkit.md` に書く。

| ひな形 | 使う所 |
| :--- | :--- |
| `TASK.template.md` | 統括・部・ライン・部下のどれも、この1つの型。`TASK.md` の名前で写して使う（ひな形の名前を TASK.md にしないのは、`TASK.md` を無視する設定に当たって git に入らないため） |
| `teamkit.template.md` | 導入したリポジトリの値の表。`.claude/teamkit.md` の名前で写して、そのリポジトリの値を書く（項目は `teamkit/docs/install.md` の2章） |
| `report.md` | ライン・部・部下の【完了】と、報告の写し（`SBI-xxx.md`） |
| `sprint_report.md` | 節目のレポート（開発推進部） |

## 1. TASK.md の型

TASK.md は、持ち手（セッション）1つに1つ。その持ち手が受け持つ仕事を**1段だけ**書き、子に任せた仕事は束の1行だけにする。中身は子の TASK.md の、束と同じ番号の枝だけが持ち、親は写さない。全体像は、束をたどって子と孫の枝を出す。

| 役割 | 置き場所 | `## タスク` に書くもの |
| :--- | :--- | :--- |
| 統括 | リポジトリ直下の `TASK.md`（置き場所で根と分かる） | ラインの作業単位（SBI）と部の仕事（`REQ-1` など）を振った行（束）。統括が自分でする仕事（`MGR-1`） |
| 部 | 値の表の「持ち手の置き場所」の `TASK.md` | 受けた依頼ごとの枝（`HAR-2-1` のように、依頼の番号に `-<連番>`）。並べて進めたい行は部下の束 |
| ライン | `.worktrees/S<番号>/TASK.md` | その作業単位の中の行（`SBI-xxx-1`、`SBI-xxx-2`…） |
| 部下 | 親が決める（`.worktrees/<任された行の番号>` など） | 任された行の中の行 |

統括のほかの置き場所は、どれも TASK.md だけを置くフォルダで、git の worktree にしない。置き場所で git を使わない（上へたどって直下の main に当たる。止まるように空を指す `.git` ファイルを置く）。コードや文書は**作業の場所**（値の表の「作業の場所」）で直す: 既定は `直下`（リポジトリ直下でブランチを切る。一度に1つの仕事だけで、使っている仕事は直下のブランチ名で分かる。塞がっていれば、持ち手が一時の worktree を作る）、`worktree` なら仕事ごとに一時の worktree（値の表の「一時の worktree」）。マージしたら片付ける（直下は既定のブランチに戻し、worktree は消す。`teamkit/docs/line_rules.md` の2章の 0 と 11）。

### 共通の決まり

- **最初の見出し**: `# <持ち手の名前>: <中身>`。持ち手の名前は「:」の前だけで決まり、セッション名と同じ文字にする（`Manager-main`、`Req-main`、`S041-main`、`SBI-041-2`）。中身は、いまの目標・依頼・作業単位の名前。Issue の番号は書かない
- **読むのは `## タスク` だけ**: その下のチェックボックスの行（いちばん浅い字下げ）が全体像に出る。持ち場・決まり・材料・メモ・申し送りの箇条書きは `- ` で書き、`- [ ]` にしない
- **`## メモ`**: 番号を付けない覚え書き（いつかやること、気づいたこと）の節。`## タスク` より下に置き、道具は読まない。管理する仕事にするときは番号を振って `## タスク` へ移す
- **行の形**: `- [ ] <番号> <名前>`。印は `[ ]`（未着手）・`[/]`（着手）・`[x]`（済み）。後ろに、この順で `（前提: …）`、`（着手: <月>/<日>）`、`（済: <月>/<日>）`、`→ <子のフォルダ>`、`#<Issue>`。`→` は Issue の手前の行の終わりに置く（行の終わりの `→` だけが束と読まれる）
  - 例: `- [ ] SBI-041 ログイン機能（前提: SBI-040）（着手: 6/2）→ .worktrees/S041 #210`
- **名前**: 何の仕事かが分かる短い言葉で、**20字まで**（前提・日付・束・Issue は数えない）。説明に回せることを括弧で書き足さない
- **説明**（任意）: 行のすぐ下に1段字下げして `- 説明: …` を1つ。**何をして、どうなれば済みか**（作るもの・直す所・確かめること）を書く。送り先への指示と経緯は伝言・申し送り・Issue に。長くなれば、さらに字下げした行で続ける。一覧と図で名前を押すと出る（`teamkit/docs/taskmd.md` の2章）
  - 例: `- [ ] SBI-041 ログイン機能` の下に `  - 説明: メールとパスワードでログインできるように。見本のアカウントでログインできれば済み`
  - 名前が20字を超える行は、持ち主が自分の未済の行を短い名前と説明に直す（済んだ行は直さない。道具は長い行も読む）
- **番号**: 英大文字で始まる語 `-` 英数字（`SBI-041`、`HAR-2`）。**SBI はラインの仕事だけ**（機能追加や実装へまっすぐ進む縦の仕事）。部の仕事は部ごとの番号（`REQ-`・`HAR-`・`TST-`・`DEV-`）で、番号の頭で持ち手が分かる。子の行は親の番号に `-<連番>`（`SBI-041-2`）。`## タスク` の行には、統括の行も含めて全部に番号を書く（番号のない行は道具が数えない。覚え書きは `## メモ` へ）。統括が自分でする仕事は `MGR-1` から統括が振る（台帳に載せない）。番号は台帳の持ち主（要求分析部）が振り、SBI を新しく切るときは人に確かめる（SBI は粗く。仕事が増えたら、まず既存の SBI の子の行に入れる）
- **束**: 子に任せた行の終わりに `→ <子の TASK.md のフォルダ>`（リポジトリ直下からの相対。`/` を含む形か `./` で始める。`->` も可）。束には番号が要る。束は、子の TASK.md の行のうち、番号が束と同じか、束の番号に `-` で続く行（**枝**）だけを指す。子が自分で始める仕事も、親に束を書いてもらう
  - **束には印を書かない**（`[ ]` のまま）。進行中か済んだかは、道具が枝から求める。子の【完了】を受けても、親は束を書き換えない
- **前提**: `（前提: <番号>, <番号>）`
  - **待ちになるのは、書いた前提と、順番**。順番は、同じ TASK.md で自分でやる行の1つ前の未済の行（順番の線）。1つの持ち手は自分の行を上から1つずつ進めるので、順番を暗黙の前提にする
  - **束（任せた行）は順番に入らない**。書いた前提だけで待つ。並べて進めたい行は部下に任せる（束にする）
  - **前提を書くのは親の TASK.md だけ**。子（部・ライン・部下）の TASK.md の中の行には、ほかの持ち手の番号を前提に書かない。持ち手をまたぐ待ち合わせは、親の行（統括なら束の行）の前提で表し、前提が済んだら親が子に知らせる
  - 書くのは、ほかの持ち手の仕事を待つとき。自分の `## タスク` の中の順番は、行の並びで足りる（1つ前の行を前提に書かなくてよい）。人の作業（`update` など）は、子の行にも書いてよい
  - 番号はツリー全体（直下の TASK.md から束をたどって読める行の全部）で探す。行の先頭の番号でも、行の最後の Issue の番号（`#146`）でも引ける。見つからない番号は着手不可になる（書き間違いに気づけるように）
  - 番号の形でない語（`（前提: update）`、`（前提: 人の返事）`）は**人の作業**。済んだら、その TASK.md の持ち主が前提を消す（自分でやる行なら `[x]` を付けてもよい）
  - 前提の案は `planning` スキル（「計画を立てて」）で起こし、人に確かめてから書ける。「計画を出して」で、空き・始められる・人待ち・待ちが出る（`overview` スキル）
- **日付**: 予定は着手の日だけ。年は書かない（今日に近い年と読む）。全部の行に要るわけではなく、書いた行にだけある
  - 着手予定日 `（着手: 6/2）`: 統括の TASK.md の行（ラインの SBI と部の仕事の行）は統括が順番を決めるときに書く。部・ラインの中の行は持ち手が書く。予定を引き直したら上書きする（最初の予定は残さず、理由は申し送りに）
  - 済んだ日 `（済: 6/3）`: `[x]` を付けるときに、付ける人（自分でやる担当）が書く。着手した日は書かない（着手は `[/]` で分かる）
  - 前倒し・遅れの印は書かない。人が日付を見て把握する
- **印は、その行を自分でやる担当だけが書く**: 取りかかるときに `[ ]` を `[/]` に、済んだら `[x]` と済んだ日。束には書かない。🔄 は道具が求める（`[/]` の行と、枝に `[/]` か `[x]` があって全部は済んでいない束。セッションが動いているかでは決めない。`teamkit/docs/taskmd.md` の2章）
  - 前提が残っている `[/]` の行も 🔄 になり、残る前提は図の下の一覧の「ブロッカー」に出る
  - **人を待っている持ち手**（その持ち手か任せた先が、人の確認や判断を待っている）は、呼び出す側が渡す（`tasktree.py --waiting <持ち手>`。`overview` スキルは Claude Code のセッションの一覧から渡す）。その持ち手に任せた束は人待ちになる
- **済んだ行はスプリントの終わりまで残す**: `[x]` の行も、枝が全部済んだ束も消さない。終わりに開発推進部が全部の TASK.md を写しの置き場（値の表）へ木ごと写し、済んだ行を片付ける（持ち主だけが書く、の例外。申し送りには触れない）。未完の行は番号を変えずに残る（`teamkit/docs/taskmd.md` の4章）
- **再開文と立ち上げの指示文は、`<パス>/TASK.md を読んで…` で書き出す**（「.worktrees/S041/TASK.md を読んで再開して」）。どの TASK.md の持ち手かが、書き出しで人にも道具にも分かる。パスはリポジトリ直下からの相対。統括だけはパスなし（「TASK.md を読んで再開して」）。書き出しの前に別の文を置かない
- 本文の地の文に「## 」付きの節の名前を書かない（「末尾の申し送りの節」と書く）。**文の折り返しで行頭が「## 」や「# 」にならないようにする**（見出しとして読まれ、節がこわれる）
- **フェーズ**（ひな形の `フェーズ: <名前>` の行）: その持ち手のいまの段階の名前（例 `要求`・`設計`・`実装`・`運用`）。人と、TASK.md を読むほかの道具への目印で、teamkit の部品は読まない。使わなければ行ごと消してよい
- 末尾に申し送りの節を置く（`handover` スキル）
- TASK.md は git に入れない（`.gitignore` に `/TASK.md`）。持ち主だけが自分の TASK.md を書く（例外はスプリントの終わりの片付け）
- 型を直すのはハーネス部。入れる時機は統括が決める。動いているラインは今の型のまま終え、次に立つラインから新しい型を使う

### 統括

- `## タスク` には、ラインに振った作業単位（SBI）の行と、部に振った部の仕事（`REQ-1` など）の行（束）、統括が自分でやる仕事（`MGR-1`）を書く。ライン1本は作業単位1つなので、行もその作業単位の1行。部には依頼ごとに束を1つ（同じ部を指す束が並んでよい。それぞれ自分の番号の枝だけを指す）。持ち手をまたぐ待ち合わせは、ここの前提で表す
- 束には印を書かない。統括が自分でやる `MGR-` の行だけ、`[/]`・`[x]` を書く
- 統括の TASK.md は git の外に置いたまま（報告の写しのような PR は出さない）
- **目標を切り替えるとき**:
  1. 全部の TASK.md を、写しの置き場（値の表の「写しの置き場」）へ木ごと写す。形はスプリントの終わりと同じ（区切りのフォルダの中に、根の TASK.md と束のフォルダの相対の位置を保って全文を写す。`teamkit/docs/taskmd.md` の4章）
  2. 目標の Issue には、目標と閉じた理由だけを数行書いて閉じる（題は「目標（済）: <目標>」。なければ立てる）。写しの場所（区切りのフォルダの名前）を1行添える
  3. 新しい目標で TASK.md を作り直す（見出し・フェーズ・`## タスク`・申し送り）。`## タスク` には、前の目標から持ち越す行（動いているラインや部への依頼）だけを番号を変えずに残し、済んだ行は消す（写しにある）。申し送りの決まったことも、次の目標に要るものだけにして、古い経緯は写しを指す

### 部

部の役割は長く続き、依頼をいくつも受ける。部への依頼は部の番号の仕事にする（相談や調べものも。`HAR-2`）。ラインと型の上の違いはない。

- 見出しの中身は、いま進めている依頼の名前（`# Harness-main: 型と決まりを新しい体制に`）か、役割をひとこと
- `## タスク` には、受けた依頼ごとの枝を並べ、上から1つずつ進める（`HAR-2-1`・`HAR-2-2`・`HAR-3-1` のように、依頼の番号に `-<連番>`。依頼をそのまま1行でするなら `HAR-3` の1行でもよい）。ほかの持ち手の番号を前提に書かない（待ち合わせは統括の行の前提）
- 並べて進めたい依頼や行は、部下に任せる（`- [ ] HAR-3-2 <名前> → .worktrees/HAR-3-2`）。部下を何本立てるかは部が決める
- 依頼が済んだら: 行に `[x]` と済んだ日を付け、統括へ【完了】を送る。済んだ行は消さず、スプリントの終わりの片付けを待つ（済んだ仕事の一覧の節は持たない。済んだ仕事は写しに残る）

例（依頼2つと部下の束）:

```markdown
## タスク
- [x] HAR-2-1 値の表を直す（済: 6/2）
- [/] HAR-2-2 スキルを直す
  - 説明: 行の書き方を新しい型に。スキルのテストが通れば済み
- [ ] HAR-3-1 フックの案を作る
- [ ] HAR-3-2 古いスキルを調べる → .worktrees/HAR-3-2
```
- 持ち場と部ごとの決まりは、持ち場・決まりの節に書く（共通の決まりは写さない）

### ライン

- **作業単位1つに1本**。統括が、前提が済んだ作業単位にラインを立て（置き場所に TASK.md を置いて立ち上げの指示文を送る）、マージして【完了】を送ったら閉じる。作業単位の切り替えはない
- セッション名は `S<番号>-main`、置き場所は `.worktrees/S<番号>`（TASK.md だけ）、ブランチは `SBI-<番号>`。コードは作業の場所（値の表。直下か一時の worktree）で直す
- TASK.md の下書きは統括が台帳から作る（`line-start` スキル）。`## タスク` には、作業計画（台帳の節）から作業単位の中の行を `SBI-<番号>-<連番>` で書く。ほかの持ち手の番号を前提に書かない
- 持ち場の節に、作業計画の「触る所」と、並行するラインの持ち場（触らない所）を名指しで書く
- 進め方は `teamkit/docs/line_rules.md` と、値の表（ポート、テストの流し方、報告の写し先）
- 大きいときは部下を立てる（行の終わりに `→ <部下のフォルダ>`。部下のセッション名は任せた行の番号そのもの `SBI-041-2`）。本数はラインが決める

### 部下

- 型は同じ。見出しは `# SBI-041-2: <任された仕事>`、`## タスク` の行は `SBI-041-2-1` から
- 【完了】は親（ラインか部）へ送る

## 2. 報告とレポート

- 【完了】・【報告】と報告の写しの型は `report.md`。最後の2行「人が判断すること:」「止まっている:」は省かない（`teamkit/docs/line_rules.md` の報告の型）
- 報告の写しは `SBI-<番号>.md` の名前で、値の表の「報告の写し先」に置き、PR に入れる
- 節目のレポートは `sprint_report.md`
