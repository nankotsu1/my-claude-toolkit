# 設計の考え方（teamkit の芯）

マルチセッションにすると仕事量は増えるが、人の理解がボトルネックになり、セッション同士の連携も取りづらくなる。teamkit の核は、タスクをツリー構造を前提に定義し、各セッションのタスクを composite 的に繋ぎ合わせられるようにして、情報を一元管理することである。

型・見え方・体制・決まりの文書（`taskmd.md`・`views.md`・`roles.md`・`line_rules.md`）は、どれもこの考え方から決めている。迷ったときは、ここに戻る。

## 1. 何が問題になるか

セッションを増やすと、作業の量と並行度は上がる。一方で、次の二つが上がらないまま残り、そこが全体の上限を決める。

| ボトルネック | 起きること |
| :--- | :--- |
| 人の理解 | 人が把握できる量は増えない。全体が見えないまま承認を求められ、承認が難しく、遅くなる |
| セッション間の連携 | それぞれが自分の会話の中だけで状態を持つ。誰が何をしていて、何を待っているかが、互いにも人にも分からない |

どちらも「情報がセッションごとに分断されている」ことが根である。だから解くべきは、分断された情報を1つの全体として扱えるようにすることだ。

```text
セッションを増やす ──→ 作業の量と並行度が上がる
        │
        └─→ 情報がセッションごとに分断される
                ├─→ 人の理解が追いつかない（承認が難しく、遅い）
                └─→ セッション同士が互いの状態を知らない
                          │
                          ▼
              composite のツリーで分断をつなぐ
                          │
                          ▼
      人にもセッションにも、同じ一つの全体が見える
                ├─→ 人: 根から全体を見て、判断だけをする
                └─→ セッション: 聞かずに互いの状態を知る
```

## 2. 核: ツリーを前提にしたタスク定義と composite

各セッションは、自分のタスクを同じ型のノード（`TASK.md`）1つに定義する。親のノードは、子に任せた仕事を1行として持ち、その行は子のノードの中の同じ番号の枝を指す（ノードは持ち手ごと、依頼は枝ごと）。ラインも部も同じ形で、違うのは寿命だけ。葉も束も同じ型なので、どのノードからでも、その下をたどれば一つの全体として扱える（composite）。

- **繋ぎ合わせる**: セッションを足すには、親に束の行を1行足すだけ。形を平らにも深くもできる
- **一元管理**: 情報は各ノードに1か所だけ置き、親は写さずに参照する。どこから読んでも同じ事実に行き着き、食い違いが起きない
- **縦と横**: 親子（誰が持つか）はツリーで、待ち関係（何が何を待つか）は枝を越えた前提で表す。一つの全体の上で、両方をたどれる

composite が効いているのは次の2点である。

| 性質 | 中身 | 効いている所 |
| :--- | :--- | :--- |
| 形の柔軟さ | 葉も束も同じ型なので、広いツリーも深いツリーも同じ決まりで扱える。足すのも組み替えるのも、束の行1行で済む | ツリーの形が決め打ちでなく、状況に合わせて選べるものになる。広さと深さのトレードオフを、その時々で選べる |
| どこからでも全体として見られる | どのノードを根にしても、その下を1つの全体としてたどれる | 人は根から、各セッションは自分を根にして見る。立つ位置が違うだけで同じ情報を見ているので、一元管理が成り立つ |

広いツリーにも深いツリーにも、原理的には対応できる。ただし、人が一目で見られる量、深くしたときの中継の遅れ、道具がたどる3段までの上限は残る。composite はその限界を消すのではなく、形をどこに置くかを後から選べるようにする。

この核が、二つのボトルネックに同時に効く。人は根のノードから全体を一目で見て、自分を待つものだけを判断すればよい。セッション同士は、相手に聞かずに、同じ全体から互いの状態を知れる。

## 3. 核を支える仕組み

1. **状態は1か所にだけ書く**。着手 `[/]` と済み `[x]` を書くのは、その仕事を自分でやる担当だけ。任せた束の状態と、人待ち・待ち・進みは、道具がノードをたどって求める。親が子の状態を書き写すと一元管理が崩れるため
2. **読む部品は1つ**。人向けの図、作業計画、セッションが答える文字の全体像が、同じ読み方を使う
3. **人には判断だけを届ける**。セッション間は短い定型文を1通、人へは推奨の案つきの問い。全体は一元管理されているので、連絡に状態の説明を載せなくてよい
4. **会話は消えてもよい**。各ノードに申し送りを残し、セッションを入れ替えてもノードは残る
5. **区切りごとに写して空にする**。スプリントの間は済んだ仕事もノードに残し、終わりに木ごと写して片付ける。過去の木は、写しから同じ道具で見られる

## 4. トレードオフと割り切り

セッションのツリーには、グラフ構造としてのトレードオフがある。設計はそれを解消せず、composite によって形を変えやすくしておくことで備える。

| 形 | 得るもの | 失うもの |
| :--- | :--- | :--- |
| 広い（親＋多くの子） | 連絡が1回で届く。誰に聞くかが明らか | 親に報告・質問・振り分けが集まる。子同士の衝突が増える |
| 深い（中間を挟む） | 親に上がる量を中間で減らせる | 中継が遅くなり、言い換えるたびに意図が薄れる |

- 割り切り: 浅いツリーを基本にする。平らに始め、親が詰まった所だけ中間を挟む。深さは3段まで
- 子の数の上限は、親の能力よりも、仕事を衝突なく持ち場に分けられる数で決まる
- 残る細い節: 連絡がすべて通る中継役と、承認をする人。どちらも取り除かず、可視化と短い連絡で「1回あたり」を軽くする
- 道具が振り先を勧めたり、時間の見通しを立てたりはしない。書き足す量が増え、手で書くものを最小限にする方針とぶつかるため

## 5. teamkit での仕組み

| 考え方 | teamkit での仕組み |
| :--- | :--- |
| ツリー前提のタスク定義 | 各持ち手の `TASK.md`（同じ型。`taskmd.md`、ひな形 `templates/TASK.template.md`） |
| composite で繋ぐ | 束の行 `→ <子のフォルダ>` が、子のノードの中の同じ番号の枝を参照する。待ちは `（前提: REQ-3）` |
| 状態は1か所 | 担当が自分のタスクに `[/]`（着手）と `[x]`（済み）を書く。束には書かず、子から求める |
| 一元管理と読み出し | 部品 `tasktree.py` がツリーをたどる（見え方の正は `views.md`）。図、作業計画、「全体像を出して」「計画を出して」（`overview` スキル）が同じ部品を使う |
| 判断だけを人に | セッション間は SendMessage の【依頼】【完了】【質問】（`line_rules.md`）。人へは AskUserQuestion |
| 会話は消えてもよい | `TASK.md` の「申し送り」の節（`handover` スキル）。`/clear` のあとはそこから再開 |
| 区切りごとに写して空にする | スプリントの終わりに、根のノードの持ち手が開発推進部に任せて、木ごと git の外へ写して片付ける（`sprint-end` スキル） |

具体的な体制は `roles.md`、印と行の書き方は `taskmd.md`、連絡の型と `/clear` の時機は `line_rules.md` と `handover` スキルにある。
