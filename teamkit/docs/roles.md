# 体制の形

エージェント（Claude Code のセッション）のチームで開発するときの、部とライン、人とのやりとり、標準の流れ。どのリポジトリでも使う部分だけを書く。リポジトリごとの値（部の置き場所、持ち場のファイル、テストの流し方、本番の禁止）は、導入したリポジトリの値の表 `.claude/teamkit.md` と、そこから指す文書に書き、食い違うときはそちらに従う。語の意味は末尾の「用語」。

- TASK.md の型と、番号と名前の決まりは `taskmd.md`（2章・3章）
- ラインの決まり（ラインの一生、進め方、実機確認の流れ）は `line_rules.md`
- 実機確認が要るかの基準は `verify.md`
- 報告とレポートの書き方は `../templates/`

## 1. 部とライン

セッション名は、TASK.md の最初の見出しの持ち手の名前と同じ文字にする（`taskmd.md` の2章）。

| 名前（セッション名） | 立て方 | 役割 |
| :--- | :--- | :--- |
| 統括マネージャー（`Manager-main`） | 常設 | 作業単位をまたいだ段取り（実行の順番、並列、どのラインに振るか、部をまたぐ待ち合わせ。結果は TASK.md の前提に書く）。セッション間の横の連携のハブ。全体の進み具合、Issue の管理、目標の切り替え |
| 要求分析部（`Req-main`） | 必要なときだけ | 人と要求をすり合わせ、要求 → 機能 → 計画を書く。作業単位の切り出しと番号、作業単位ごとの作業計画（何を作り、どう確かめ、どこを触るか）、技術的な依存の事実（順番は決めない）。調べもの |
| ハーネス部（`Harness-main`） | 必要なときだけ | 開発のサイクルを円滑かつ安全に回す土台。決まり・型・スキル・フック・権限の変更案 |
| テスト部（`Test-main`） | 必要なときだけ | CI、テストの土台、AI レビューの基準、目視レポート、実機確認の基準 |
| 開発推進部（`Dev-main`） | 常設寄り | 節目のレポート、点検、不要なものの整理、改善の受付（人の改善要望と不具合の報告を聞き取って Issue にし、統括へ渡す）。スプリントの終わりの写し・レトロ・片付け（統括から任される。3章） |
| ライン（`S<番号>-main`） | 作業単位1つにつき1本。済めば閉じる | 作業単位1つを、実装 → テスト → セルフレビュー → PR → 実機確認 → マージまで、1つのセッションで通す。大きいときは部下（`SBI-<番号>-<連番>`）を立てる |

- 部は、リポジトリを横断する関心事を整える。ラインは、機能追加や実装へまっすぐ進む。だから作業単位の番号（`SBI-123`）はラインの仕事に限り、部の仕事は部ごとの番号（`REQ-1`・`HAR-1`・`TST-1`・`DEV-1`）で数える。番号の頭で持ち手が分かる。台帳に載らない仕事を Issue 1つを地図にして進めるときは、地図の Issue を SBI と同じに扱い、番号は `I-<Issue の番号>`（`taskmd.md` の3章）
- ラインと部は、TASK.md の型の上では同じ形（`taskmd.md`）。違うのは寿命（ラインは作業単位が済めば閉じ、部は依頼を受け続ける）と、番号の頭だけ
- **部下の本数は、任せる持ち手が決める**（部もラインも）。人への質問が重なりすぎないよう本数を調えるのも、その持ち手の役目。統括は持ち手の中の並列に口を出さない。部下の【完了】は任せた持ち手が受け、統括へはその持ち手が送る
- 仕事の少ない部も、部として持つ（体制の形がいつも同じなので、部を立てたときに型や決まりを変えずに済む）。立てるのは要るときだけでよい
- 3段のツリーとの対応: 根 ＝ 統括。束 ＝ 部とライン。葉 ＝ 部下

## 2. 人とのやりとり

- 人は、判断・承認・確認が要る場面で、そのセッションと直接やりとりする。統括は唯一の窓口ではない
- セッション間の横の連携は、統括をハブにする。1行目で用件が分かる定型を使う: 【依頼】（統括 → 部・ライン）、【完了】【質問】（部・ライン → 統括）、【回答】【連絡】（統括 → 部・ライン）。【完了】の書き方は `../templates/report.md`

| セッション | 人が関わる場面 |
| :--- | :--- |
| 要求分析部 | 要求の優先度、仕様のすり合わせ、画面や出力の案の選択 |
| ライン | 設計の大事な分かれ目、実機確認、マージの許可 |
| テスト部 | 目視レポートの確認、検証の基準の変更の承認 |
| ハーネス部 | 決まり・型・フック・CI など開発の規律に関わる変更の承認 |
| 開発推進部 | 節目の振り返り、改善の受付、次の改善の合意 |
| 統括 | 目標、順番と振り先の相談、全体の進み具合 |

## 3. 標準の流れ

1. 要求分析部が人と要求を詰め、作業単位と依存の事実を台帳に書く
2. 統括が順番と振り先を決めて、自分の TASK.md の前提に書く。前提が済んだ作業単位にラインを立てる（`line-start` スキル）
3. ラインが実装・テスト・セルフレビュー・PR・実機確認・マージまで通し、【完了】を送って閉じる（`line_rules.md`）
4. スプリントの終わりに、開発推進部が写し・レトロ・片付けをする（`taskmd.md` の4章。区切りは根の持ち手の統括が受け持ち、開発推進部に任せる）。レトロでは、レポートと点検をし（`../templates/sprint_report.md`）、未完のタスクを次の計画に組み込む案を出す。仕組みの課題は統括経由でハーネス部へ

- 依存の事実は文書を書く側（要求分析部）が一番よく知り、順番は全体を見る側（統括）が決める
- 持ち手をまたぐ待ち合わせは、統括の行の前提で表す。子の TASK.md の行には、ほかの持ち手の番号を前提に書かない（`taskmd.md` の2章）。前提が済んだら統括が【連絡】で知らせる
- 状態の印（着手 `[/]`・済み `[x]`）を書くのは、その仕事を自分でやる担当だけ。任せた束には、統括も部長も印を書かない（`taskmd.md` の2章）
- 実装と検証を別のセッションに分けない（流れが切れるので、検証からマージまで実装したラインで通す）

## 4. 持ち場の分離

- TASK.md を書くのは持ち主だけ。例外は、スプリントの終わりの片付け（開発推進部。持ち手が止まっているときに済んだ行を消し、申し送りには触れない）
- 仕様書を書き換えるのは要求分析部だけ
- 並行するラインどうしは、作業計画の「触る所」を分ける
- ハーネス部の決まり・検証の変更と、テスト部の検証の基準を緩める変更は、人の承認を通す
- 本番への反映（インストールや更新）は人だけが行う
- 型や決まりの変更を main に入れる時機は統括が決める。動いているラインは今の型のまま終え、直した型は次に立つラインから使う
- 各ラインが自分でマージするので、統合の確認は CI（PR を main と合わせた状態でテストする）と、PR の前とマージの直前に main を取り込み直すことで補う（`line_rules.md` の2章）

## 5. セッションの区切り

- どのセッションも、区切りごとに TASK.md の末尾の申し送りを書き、`/clear` して、自分の TASK.md から再開する（`handover` スキル）
- 切るのは、人が長く離れる見込みのとき、作業の区切り、コンテキストが大きくなったあとの最初の区切り。やりとりが続いているときと、コンテキストが小さいうちは切らない（再開の費用を取り戻せないため）
- `/clear` は人が打つ。セッションは最後に「/clear のあと」と文で書き、再開文だけをコードブロックで出して止まる
- 統括の目標を切り替えるときは、今の TASK.md を写しの置き場に写し（`taskmd.md` の4章）、目標の Issue には目標と閉じた理由だけを書いて閉じ、新しい目標で作り直す（`../templates/README.md` の「統括」）

## 6. 用語

| 語 | 意味 |
| :--- | :--- |
| セッション | Claude Code の会話1つ。統括・部・ライン・部下は、どれも1つのセッション |
| 持ち手 | 仕事を受け持つセッション。名前は TASK.md の最初の見出しの「:」の前で、セッション名と同じ（`Manager-main`、`S041-main`） |
| 統括 | 全体の段取りを受け持つ持ち手。TASK.md はリポジトリ直下に置き、全体像の根になる |
| 部 | リポジトリを横断する関心事（要求、決まりと道具、テスト、記録と改善）を受け持つ持ち手。依頼が入れ替わりながら長く続く |
| ライン | 作業単位1つを、実装からマージまで通す持ち手。済めば閉じる |
| 部下 | ラインや部が、大きい行や並べて進めたい行を任せるために立てる持ち手。本数は任せる持ち手が決める |
| 作業単位（SBI） | ライン1本が通す縦の仕事1つ。SBI は Sprint Backlog Item の略（`taskmd.md` の3章） |
| 台帳 | 作業単位ごとの作業計画（何を作り、どう確かめ、どこを触るか、依存の事実）の一覧。要求分析部が書く。場所は値の表 |
| 行 | TASK.md の `## タスク` のチェックボックス1つ。仕事1つ。番号が要る |
| 束 | 子の持ち手に任せた行。行の終わりの `→ <子のフォルダ>` で表し、中身は子の TASK.md の枝にある |
| 枝 | 束が指す、子の TASK.md の中の行。番号が束と同じか、束の番号に `-` で続く行 |
| スプリント | 仕事の区切り。終わりに全部の TASK.md を写して、済んだ行を片付ける（`taskmd.md` の4章） |
| 直下 | リポジトリ直下（最初に clone したフォルダ。人が VS Code で開いている所）。統括の TASK.md を置く |
| 置き場所 | 持ち手の TASK.md を置くフォルダ。統括は直下、ほかの持ち手は TASK.md だけのフォルダ（`.worktrees/S041` など。git の worktree にしない。`taskmd.md` の2章） |
| 作業の場所 | コードや文書を直してコミットする所。直下でブランチを切るか、一時の worktree。どちらを既定にするかは値の表の「作業の場所」（`line_rules.md` の2章の 0） |
| 一時の worktree | 仕事ごとに `origin/main` から作る git の worktree。作業の場所が worktree のときと、直下が塞がっているときに使い、マージしたら消す。場所は値の表 |
| 写しの置き場 | スプリントの終わりと目標を閉じるときに、TASK.md を木ごと写す所。git の外。場所は値の表 |
| 前提 | 行が待つもの（ほかの行の番号か、人の作業）。`（前提: …）` |
| 人の作業 | 前提に書く、番号でない語（`update`、`人の返事`）。人が済ませるのを待つ |
| 申し送り | TASK.md の末尾の節。止まっても後任がすぐ再開できるように、いまの状態を書き残す |
| 実機確認 | マージの前に、人が変更を本番の環境で目で見て確かめること（`verify.md`） |
| 目視レポート | 画面や出力の画像を並べて、人が目で見て確かめるための報告。テスト部が作り、人が確かめる |
| 空き | やりかけの仕事も、始められる仕事もない持ち手。統括が次の仕事を振れる相手（求め方は `views.md` の3章） |
| 全体像 | TASK.md を束でたどって、全部の持ち手の仕事と状態を1つのツリー・計画・図にしたもの（`views.md`） |
| 値の表 | 導入したリポジトリの `.claude/teamkit.md`。そのリポジトリだけの値（ポート、台帳の場所、報告の写し先、本番の禁止 など）を書き、スキルとスクリプトが読む |
