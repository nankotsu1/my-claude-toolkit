# ラインの決まり（共通）

作業単位のライン（`S<番号>-main`）と、その部下に共通の決まり。セッションの始めに1回読む。リポジトリごとの値（テストの流し方、ポート、報告の写し先、本番の禁止 など）は、導入したリポジトリの値の表 `.claude/teamkit.md` と、そこから指す決まりの文書にあり、食い違うときはそちらに従う。作業単位ごとの値（作る行、触る所）は `TASK.md` にあり、食い違うときは `TASK.md` に従う。

## 1. ラインの一生

- **作業単位1つに1本**。統括（`Manager-main`）が、前提が済んだ作業単位にラインを立てる（置き場所 `.worktrees/S<番号>` に TASK.md を置いて、立ち上げの指示文を送る。下書きは `line-start` スキル）
- ラインの置き場所は、部と同じく TASK.md だけを置くフォルダで、git の worktree ではない。**置き場所で git を使わない**（上へたどってリポジトリ直下の main に当たる。止まるように、置き場所には空を指す `.git` ファイルを置く）。コードと文書は、**作業の場所**（値の表の「作業の場所」。既定はリポジトリ直下、塞がっていれば一時の worktree。下の2章の 0）で、ブランチ `SBI-<番号>` を切って直す
- ラインの TASK.md の行には、ほかの持ち手の番号を前提に書かない（前提を書くのは親の TASK.md だけ）。ほかのラインや部の仕事を待つことは統括の行の前提で表し、済んだら統括が【連絡】で知らせる。待つと分かったら、統括に【質問】で知らせる
- ラインは、実装 → テスト → セルフレビュー → PR → 実機確認（要るときだけ）→ マージを、1つのセッションで通す。実装と検証を別のセッションに分けない
- マージして【完了】を送ったら閉じる。次の作業単位へ切り替えない（次は別のラインが立つ）
- 大きいときは部下を立てる。任せた行の終わりに `→ <部下のフォルダ>` を書き、部下のセッション名は任せた行の番号（`SBI-<番号>-<連番>`）にする。部下の【完了】はラインが受ける

## 2. 進め方

0. 作業の場所を用意する（値の表の「作業の場所」）。ここから先のコマンドは、その場所で動かす。どちらで作業しているかを申し送りに書く
   - **直下**（既定）: 直下が空いているかを見る。空いているのは、直下のブランチが既定のブランチ（`main` など）で、コミットしていない変更がないとき（`git -C <直下> branch --show-current`・`git -C <直下> status --porcelain` が何も出さない）。git に入っていない新しいファイルも変更に数える（書きかけを、ほかの仕事のブランチに持ち込まないため）。生成物（`__pycache__/` など）は `.gitignore` に入れておく（`install.md` の3章）。何かが出ていれば塞がっている。空いていれば `git -C <直下> fetch origin && git -C <直下> switch -c SBI-<番号> origin/main`。直下を使っている仕事は、直下のブランチ名（仕事の番号）で分かる。塞がっていれば、下の worktree で進める
   - **worktree**（値が worktree のとき、または直下が塞がっているとき）: リポジトリ直下から `git fetch origin && git worktree add <一時の worktree> -b SBI-<番号> origin/main`（場所は値の表の「一時の worktree」）
1. 実装する。`## タスク` の行を上から進め、取りかかるときに `[ ]` を `[/]` に、済んだら `[x]` と済んだ日 `（済: <月>/<日>）` を付ける
2. テストを足す。不具合を直すときは、**直す前に失敗する**ことを確かめた再現テストにする
3. テストを通す（コマンドは値の表の「テスト（関係する所）」「テスト（全部）」）。作業の途中は、変えた所に関係するテストだけを流す。全部を流すのは PR の前の1回だけ（CI でも同じものが回るので、main を取り込んだあとや CI を通ったあとに手元で重ねて流さない）。文書だけの変更なら、その文書を読むテストだけでよい。出力は末尾だけ見て、失敗したときだけ全文を読む
4. セルフレビュー（`/code-review medium`）。あわせて、値の表の「レビューの観点」の一覧を当てる。指摘は直すか、直さない理由を PR に書く
5. 末尾の報告の節を埋め、TASK.md（置き場所のもの）を作業の場所の、値の表の「報告の写し先」へ `SBI-<番号>.md` の名前で写してコミットする。**報告の写しは PR に入れる**（main に別のコミットで入れない）
6. main を取り込み（`git fetch origin && git merge origin/main`）、PR を出す。全部のテストは手元で流し直さず、CI に任せる。手元で流すのは、取り込んだ変更が自分の変更に関係するとき（同じファイルや関数、自分の変えた所を読むテストを変えた）の、関係するテストだけ
7. CI を待つ（`gh pr checks <PR> --watch`）。出ているチェックがすべて通るまでマージしない
8. 実機確認が要る PR は、下の「実機確認」へ
9. マージの直前に、main が進んでいないかを見る（`git fetch origin && git log HEAD..origin/main`）。進んでいたら取り込んで push し、CI をもう一度待つ（手元のテストは 6 と同じく、関係するときだけ）。報告を直したら写しも直す
10. マージは次のどちらか。許可は前のセッションから引き継がない
    - AskUserQuestion（見出し「マージ」）で許可を取ってから `gh pr merge <PR> --squash`。PR の番号、CI の結果（main を取り込んだあとの回）、手元で流したテスト（流したなら件数）を書く
    - 人が GitHub で自分で squash マージする（`gh pr view <PR> --json state` が MERGED なら済み）。GitHub のコメントは許可とみなさない
11. 片付けて閉じる: `gh pr view <PR> --json state` が MERGED になったのを確かめてから、作業の場所を戻し、作業ブランチを消す（手元と origin）。直下なら `git switch <既定のブランチ> && git pull --ff-only` で直下を空きに戻す。一時の worktree なら worktree ごと消す。あわせて模擬サーバーなどのプロセスを止める。置き場所の TASK.md は消さない（スプリントの終わりに写して片付ける。`taskmd.md` の4章）。統括へ【完了】を1通送り（下の報告の型）、申し送りを書いて止まる

区切り（コミット・push・PR・返事待ち）ごとに、末尾の申し送りの節を `handover` スキルで更新する。トークンの上限は前触れなしに来る。

## 3. プルリクエスト

- タイトルは `SBI-<番号>: <作業単位の名前>`。本文に Issue があれば `Closes #<Issue>`（文書だけで実装を待つ Issue は `Refs #<Issue>`。`Closes` は説明の文の中でも閉じる）
- 本文: 変更点 / 確かめたこと（テストの件数、CI、画像） / 決めたこと / 未解決 / 実機確認の手順（要るときだけ）
- 並行するラインとマージの順番が決まっていれば、相手より先にマージしない

## 4. 実機確認

マージの前に人が目視する。本番は1つなので、一度に1本（重なったら統括が順番を決める）。

1. ラインが PR に実機確認の手順を書き、【報告】の「人が判断すること: 実機確認」に入れる
2. 人がラインの作業の場所（直下か一時の worktree）から本番に入れて（`update` など）確かめる
3. 直しは同じ PR に積む
4. OK でマージする
5. 人がリポジトリ直下から入れ直して、本番を main に戻す（直下で作業したときは、2章の 11 で直下が main に戻ってから）

- 要るかはラインが書き、基準はテスト部が持つ（`teamkit/docs/verify.md`）。文書だけの PR と、コマンドで確かめられる PR は CI だけ
- データの形を変える PR は手順に一言、フックのような入れ方の変わる PR は入れ直しの手順も書く

## 5. 他のセッションとのやりとり

- 送るのは、親への【完了】【報告】と【質問】だけ。再開したことや途中の様子は送らない。親からの【回答】【連絡】に、返事が要らなければ返事しない
- 分からないことは、まず親に【質問】で聞く。人の判断が要るもの（設計の大事な分かれ目、権限、実機の実験、マージの許可）は AskUserQuestion で直接聞く
- TASK.md に書いていない所を直す必要が出たら、親に【質問】で知らせる

### 報告の型

【完了】と【報告】は、1行目に種別と要点を書き、**最後に次の2行を置く**（ひな形は `teamkit/templates/report.md`）:

```text
【完了】SBI-<番号> をマージしました
- PR <番号>、マージ <ハッシュ>
- 持ち越し: <なければ書かない>
人が判断すること: なし
止まっている: なし
```

- 「人が判断すること:」: 仕事を終えたあと、**人に**残す事柄（実機確認、`update` の実行、次に選んでほしいこと）。受け手の道具は、これを拾って送り手を「判断待ち」にする
- 「止まっている:」: 親に答えてほしくて先へ進めない事柄
- 行頭は欄の名前ちょうど（前に「- 」や空白を付けない。コロンは半角）。中身がなければ「なし」。あれば同じ行に続けるか、次の行から「- 」の箇条書き
- 2行は省かない（「なし」の報告で、前の判断待ちが外れる）
- 人の判断が要って**いま止まる**ときは AskUserQuestion で聞く。この欄に書くのは、止まらずに仕事を終えたあとに残す事柄だけ

## 6. 読む量を抑える

- 大きな文書は全部読まない。`grep -n '^#' <文書>` で見出しの行番号を出し、その節だけを範囲を決めて読む
- TASK.md の材料の節に書いてあるもので足りないときだけ、もとの文書を引く
- コマンドの出力は `tail`・`grep` で必要な所だけ見る

## 7. 本番と重い操作

- 本番（いま自分たちが使っている道具やサーバー。値の表の「本番（触らない）」）には触れない。入れる・更新するのは人だけ
- 模擬環境は、値の表で決まった自分のポートの範囲（ラインは TASK.md のこの作業単位の値）で立てる。終わったら、模擬サーバーと一時ディレクトリが残っていないことを確かめる
- 画面のフォーカスを奪う実験や、PC 全体に重い負荷をかける操作は、AskUserQuestion で時機を聞いてから
