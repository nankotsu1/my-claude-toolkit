# 実機確認の基準（型）

ラインの PR を、マージの前に人が本番で目視するか（実機確認）を決める基準と、手順の書き方の型。流れ（PR に手順を書く → 人がラインの作業の場所から本番に入れて見る → 直しは同じ PR → OK でマージ → 人がリポジトリ直下から入れ直す）は `teamkit/docs/line_rules.md` の4章。ここには、要るかの決め方と、PR に書く手順の中身を書く。

持ち手はテスト部。リポジトリごとの値（入れるコマンド、戻すコマンド、どのファイルの変更が要るに当たるか）は、導入したリポジトリの文書（値の表 `.claude/teamkit.md` の「実機確認の基準」が指すもの）に書き、食い違うときはそちらに従う。書くことは下の4章。

## 1. 何のためか

CI と模擬環境のテストは、作った人が想定した形でしか確かめられない。実機確認は、それで見えないものを人の目で拾う: 本物のデータ、本物のアプリや OS とのつながり、人が実際に使ったときの見え方と手触り。本番は1つなので、一度に1本しかできず、人の時間も使う。だから、要る PR を絞り、要る PR では見る所を具体的に書く。

## 2. 要るかの基準

上から当てはめ、1つでも当たれば要る。迷ったら要る（省いてよいのは、下の「要らない」に当たるときだけ）。

| 要る | 例 |
| :--- | :--- |
| 人が見る画面・操作が変わる | 表示、ボタン、キー操作、並び、色。画像のテストと模擬環境の操作のテストは通っていても、本物のデータと幅で見る |
| 本番の外側とのつながりが変わる | ほかのアプリ・OS・エディタとのやりとり（前面に出す、通知、立ち上げ、フック、外部コマンド）。模擬では相手を置き換えている |
| 入れ方が変わる | 本番の設定に書く物が増える・変わる（フックの登録など）。入れ直しの手順そのものを確かめる |
| 保存するデータの形が変わる | 本番に溜まった前の形のデータを、新しい版で読めるか |
| 実データの形を推測して作った | ログや外部の出力の形を、見本ではなく推測で読んでいる |

| 要らない（CI だけ） | 理由 |
| :--- | :--- |
| 文書だけの PR | 本番に入らない |
| コマンドで確かめられる PR（テストだけ、CI の設定、本番に入らない道具や部品の文字の出力） | CI と手元のテストが同じものを見ている |

- 要るかはラインが決め、PR の本文と【報告】に書く。要らないとしたときも、PR の本文に「実機確認: 要らない（<上の表のどれか>）」と一言書く
- この基準を緩める変更（「要らない」を広げる、「要る」を外す）は、人の承認を通す

## 3. PR に書く手順の型

PR の本文の「実機確認の手順」の節に、人がそのまま上から進められる形で書く。

```markdown
## 実機確認の手順

1. 入れる: `<ラインの作業の場所>`（直下か一時の worktree）で `<入れるコマンド>`（入れ方が変わる PR は `<入れ直しのコマンド>`）
2. 見る:
   - [ ] <どの画面・どの操作> で <何が見えれば OK>
   - [ ] <前と変わっていないはずの所> が前のとおり
3. データ: <保存するデータの形を変える PR だけ。前の形のデータがどうなるか、戻したときどうなるか>
4. 戻す: マージのあと、リポジトリ直下で `<戻すコマンド>`。直さずに閉じるときも同じ
```

- 見る所は、OK と NG が人に分かる形で書く（「<画面のどこ> に <何> が出る」。「動くこと」は書かない）
- 1つの PR の見る所は、5つくらいまでに絞る。多いときは、変えた所に近い順に
- 見るために作る状態（エラーの状態、人の確認を待つ状態など）があれば、作り方も書く

## 4. 導入したリポジトリの文書に書くこと

値の表の「実機確認の基準」が指す文書に、次のものを書く。

- 入れるコマンドと、入れ直しが要る条件（入れ方が変わる変更）
- 戻すコマンド（リポジトリ直下から、main の版に戻す）
- 本番に入ったことを確かめる方法（版の表示など）
- 上の「要る」に当たる変更を、そのリポジトリのファイルや機能の名前で書いた表
- 本番に触れてよいのは人だけ、という禁止の範囲
