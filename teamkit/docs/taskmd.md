# TASK.md の型

TASK.md は、エージェント（Claude Code のセッション）1つが受け持つ仕事を書く、チェックボックスの一覧。この文書は、その**型**の要求をまとめる。型を読む道具は、全体像の部品 `teamkit/tasktree.py` と、スキル `overview`・`planning`。

- 型の細部（ひな形と書き方の手引き）は `teamkit/templates/`（`TASK.template.md` と `README.md`）にある。食い違うときは、この文書を正として、ひな形の側を直す
- 誰が何をするか（統括・部・ライン・部下）と、語の意味（持ち手、束、枝、作業単位 など）は `roles.md`
- 道具が TASK.md から何を出すか（状態の求め方、数える単位と空き、文字の全体像と計画、図）は `views.md`

## 1. 方針

- **型は1つ。語を変える設定は持たない。** どのリポジトリでも同じ型で書く。設定がないので、道具も説明も1つで済む。足りない所は、使いながら型に足す
- 全体を見て決め、1つの場面だけに合わせない。ただし一般化しすぎない（ある程度は簡単に）
- **ノードは持ち手の TASK.md、依頼はその中の番号の枝。** 親は、子に任せた仕事を束の行1つで持ち、束は子の TASK.md の中の、束と同じ番号の枝を指す。木は番号で組む。ラインも部も部下も同じ形で書き、違うのは寿命だけ
- **行は短い名前、詳しいことは説明に。** 一覧と図で読むのは名前だけにし、何をしてどうなれば済みかは、行の下の説明に分けて書く（スキルの名前と説明を分けて書くのと同じ）。説明は、押したときに初めて出す
- **状態は1か所にだけ書く。** 手で書くのは、ツリー（行と束）・前提・自分でやる行の印（着手 `[/]`・済み `[x]`）と、日付（着手予定日・済んだ日）だけ。印を書くのは、その仕事を自分でやる担当だけで、親は子の状態を写さない。束の状態と進み具合（進行中、始められる、待ち）は、道具が子の枝から求める。日付は、予定に対して前倒しか遅れかを、人が日付を見て把握するため

## 2. 決まった形

| 項目 | 決まった形 | 例 |
| :--- | :--- | :--- |
| 置き場所 | 持ち手1つに TASK.md 1つ。根は、リポジトリ直下の TASK.md（統括）。置き場所で根と分かるので、根を示す語は書かない。統括のほかの持ち手の置き場所は、TASK.md だけを置くフォルダにする（git の worktree にしない）。コードや文書を直す場所（作業の場所）は、導入したリポジトリの値で選ぶ: リポジトリ直下でブランチを切る（既定。直下は一度に1つの仕事だけで、使っている仕事は直下のブランチ名で分かる）か、仕事ごとの一時の worktree。直下が塞がっていれば、持ち手が一時の worktree を作る（`line_rules.md` の2章） | `TASK.md`、`.worktrees/S041/TASK.md` |
| 最初の見出し | `# <持ち手の名前>: <中身>`。持ち手の名前は「:」の前だけで決まり、セッション名と同じ文字にする。見出しがない・「:」がないときだけ、TASK.md のあるフォルダの名前を持ち手の名前にする。中身は、いまの目標・依頼・作業単位の名前 | `# Manager-main: 会員機能を作る`、`# S041-main: ログイン機能`、`# Req-main: 要求と仕様の受け持ち` |
| 読む節 | `## タスク` のチェックボックスの行（いちばん浅い字下げのもの）と、そのすぐ下の説明だけ。統括・部・ライン・部下のどれも同じ。`## タスク` がない TASK.md は、全体のいちばん浅いチェックボックスを読む | 下の例 |
| 行 | `- [ ] <番号> <名前>`。印は `[ ]`（未着手）・`[/]`（着手）・`[x]`（済み）。後ろに、待つものがあれば `（前提: …）`、日付があれば `（着手: …）`・`（済: …）`、子に任せたら `→ <子のフォルダ>`、Issue があれば行の最後に `#<番号>` の順。`→ <子のフォルダ>` は Issue の手前の行の終わりに置く（道具は行の終わりの `→` だけを束と読む） | `- [ ] SBI-041 ログイン機能（前提: SBI-040）（着手: 11/24）→ .worktrees/S041 #210` |
| 名前 | 番号のあとの、何の仕事かが分かる短い言葉。**20字まで**を目安にする（道具は数えない。書く人とスキルが守る）。前提・日付・束・Issue は名前に数えない（道具が外して列に出す）。説明に回せることを括弧で書き足さない | `ログイン機能`、`行の名前を短く` |
| 説明 | 任意。行のすぐ下に、1段字下げして `- 説明: …` を1つ。**何をして、どうなれば済みか**（作るもの・直す所・確かめること）を書く。送り先への指示と経緯は書かず、伝言・申し送り・Issue に書く。長くなれば、さらに字下げした行で続ける。道具は、図の下の一覧などで名前を押したときに出す（`views.md`） | `  - 説明: メールとパスワードでログインできるように。見本のアカウントでログインできれば済み` |
| 番号の形 | 英大文字で始まる語 `-` 英数字。`-` で続けて子の番号にできる。前提に書けて、道具が引けるのは、この形の語と Issue の `#番号` | `SBI-041`、`SBI-041-2`、`REQ-3`、`MGR-1` |
| 番号は全部の行に | `## タスク` の行には、統括の行も含めて全部に番号を付ける。番号のない仕事は管理の外で、`## タスク` に書かない（覚え書きは `## メモ` の節か申し送りに書く。道具はどちらも読まない）。`## タスク` に番号のない行があれば、道具は数えない | `MGR-1`、`REQ-3-1` |
| 子の行の番号 | 親の行の番号に `-<連番>` を足す。依頼をそのまま1行でするときは、親の束と同じ番号の行1つでもよい | `SBI-041-1`、`SBI-041-2`、`REQ-3` |
| 束 | 子に任せた行の終わりに `→ <子の TASK.md のフォルダ>`。束には番号が要る。束は、子の TASK.md の行のうち、番号が束と同じか、束の番号に `-` で続く行（**枝**）だけを指す。子の TASK.md のほかの行は、この束に入らない。子が自分で始める仕事も、親に束を書いてもらう（親から見えるのは束の枝だけ） | `→ .worktrees/S041` |
| 複数の依頼 | 1つの持ち手が依頼をいくつ受けても、TASK.md は1つ。依頼ごとの枝を `## タスク` に並べ、上から1つずつ進める。並べて進めたい依頼や行は、部下に任せる（束にする）。部下を何本立てるかは、任せる持ち手が決める | 下の例の Req-main |
| 前提 | `（前提: <番号>, <番号>）`。待ちになるのは、(1) 書いた前提と、(2) 同じ TASK.md で自分でやる行の、1つ前の未済の行（順番）。1つの持ち手は自分の行を上から1つずつ進めるので、順番を暗黙の前提にする。任せた行（束）は順番に入らず、書いた前提だけで待つ。番号の形でない語は**人の作業**（済んだら持ち主が消す）。**ほかの持ち手の番号を前提に書くのは親の TASK.md だけ**: 子（部・ライン・部下）の TASK.md の行には、ほかの持ち手の番号を前提に書かない。持ち手をまたぐ待ち合わせは親の行（統括なら束の行）の前提で表し、済んだら親が子に知らせる。持ち手をまたぐ待ちを1か所で見られるように。人の作業の語（`update`、`人の返事`）と、同じ TASK.md の中の行の番号は、子の行にも書いてよい。道具は子の前提も読む | `（前提: SBI-040, SBI-039-2）`、`（前提: SBI-041, update）` |
| 着手 | 自分でやる行に取りかかったら、担当が `[ ]` を `[/]` にする。束の行には書かない | `- [/] SBI-041-2 ログイン画面を作る` |
| 済み | 自分でやる行が済んだら、担当が `[x]` にし、`（済: <月>/<日>）` も書く。束の行には書かない（束が済んだかは、枝の行が全部 `[x]` かで道具が求める）。着手した日は書かない | `- [x] SBI-041-1 画面の流れを調べる（着手: 11/24）（済: 11/25）` |
| 着手予定日 | `（着手: <月>/<日>）`。予定は着手の日だけ（完了の予定は持たない）。年は書かず、今日に近い年と読む。書くのは、統括の TASK.md の行（部やラインに振った行）は統括が順番を決めるとき、部・ラインの中の行は持ち手。全部の行に要るわけではなく、書いた行にだけある。予定を引き直したら上書きする（最初の予定は残さない。理由は申し送りに） | `（着手: 11/24）` |
| 前倒し・遅れ | 道具は判定も印も出さない。人が日付を見て把握する（印を足すと見る所が増えるため）。道具は日付を文面から外し、一覧の左の列（状態・着手・済）に出す。図の下の一覧は、状態によらず着手日の順に、済んだ行も混ぜて1つの表で並べる（日付のない行はあと） | |
| 進行中（🔄） | `[/]` の行と、枝に `[/]` か `[x]` があって全部は済んでいない束。セッションが動いているかでは決めない。前提が残っている `[/]` の行も 🔄 にし、残る前提はブロッカーに出す | |
| 始められる・人待ち・着手不可 | `[ ]` の行と、枝に印のない束（枝の行がまだない束を含む）は、前提から求める。前提が全部済んでいれば始められる、人の作業だけが残れば人待ち、ほかの番号が残れば着手不可。呼び出す側が**人を待っている持ち手**を渡したときは、その持ち手に任せた束も人待ち | |
| 束の持ち手 | 束の行の仕事は、子の持ち手のもの。子がまだ枝の行を書いていなくても、子の持ち手の仕事として数える（その持ち手は空きではない） | |

**人を待っている持ち手**は、その持ち手か任せた先が、人の確認や判断を待っていること。呼び出す側が持ち手の名前で渡す（任意）。渡さなくても、図と一覧は TASK.md だけで進みに合わせて出る。求め方の細部（数える単位、空き、図の描き方）は `views.md`。

例（統括と、部1つ、ライン1本）:

```markdown
# Manager-main: 会員機能を作る

## タスク
- [ ] REQ-3 認証の要求 → .worktrees/Req
- [ ] REQ-4 通知メールの要求 → .worktrees/Req
- [ ] SBI-041 ログイン機能（前提: REQ-3）→ .worktrees/S041
  - 説明: メールとパスワードでログインできるように。見本のアカウントでログインできれば済み
- [ ] MGR-1 公開の時機を決める（前提: SBI-041, 人の返事）
```

```markdown
# Req-main: 要求と仕様の受け持ち

## タスク
- [x] REQ-3-1 認証の方式を調べる
- [x] REQ-3-2 要求を書く
- [/] REQ-4-1 通知の文面を詰める
- [ ] REQ-4-2 メール配信サービスを比べる（大きいので部下に任せる）→ .worktrees/REQ-4-2
```

```markdown
# S041-main: ログイン機能

## タスク
- [x] SBI-041-1 画面の流れを調べる
- [/] SBI-041-2 ログイン画面を作る
- [ ] SBI-041-3 パスワードの再設定
```

統括の束 REQ-3 と REQ-4 は、どちらも Req-main の TASK.md を指すが、REQ-3 は `REQ-3-…` の行だけ、REQ-4 は `REQ-4-…` の行だけを枝に持つ。REQ-3 は枝が全部済んだので済み、REQ-4 は枝に `[/]` があるので進行中。全体像（`tasktree.py --text`）にはこう出る（済んだ行は「済 n 件」に畳む。書き出しの形と、図・計画は `views.md`）:

```text
# Manager-main: 会員機能を作る
- ✅ 済 1 件
- 🔄 REQ-4 通知メールの要求 0/2
  - （.worktrees/Req/TASK.md）
  - 🔄 REQ-4-1 通知の文面を詰める
  - ⬜ REQ-4-2 メール配信サービスを比べる（大きいので部下に任せる）
    - （.worktrees/REQ-4-2/TASK.md）
    - タスク一覧はありません
- 🔄 SBI-041 ログイン機能（前提: REQ-3） 1/3
  - （.worktrees/S041/TASK.md）
  - ✅ 済 1 件
  - 🔄 SBI-041-2 ログイン画面を作る
  - ⏳ SBI-041-3 パスワードの再設定
- ⏳ MGR-1 公開の時機を決める（前提: SBI-041, 人の返事）
```

## 3. 名前と番号

**SBI** は Sprint Backlog Item（スクラムのスプリントバックログの項目）の略で、ここでは**ライン1本が始めから終わりまで通す縦の仕事1つ**（機能の追加や実装へまっすぐ進む仕事）を指す。作業単位とも呼ぶ。番号の正式な書き方は `SBI-123`（ハイフンあり、3桁でゼロ埋め。1000 からは4桁）。`S123` は、ラインのセッション名とフォルダにだけ使う略。

| 出る所 | 名前 |
| :--- | :--- |
| 作業単位の番号 | `SBI-123` |
| 統括の TASK.md の行 | `- [ ] SBI-123 <名前> → .worktrees/S123` |
| ラインのセッション名（全体像の持ち手） | `S123-main` |
| ラインの置き場所（TASK.md だけを置くフォルダ） | `.worktrees/S123` |
| ブランチ | `SBI-123`（ライン1本が作業単位1つなので、番号だけ） |
| ラインの中の行 | `SBI-123-1`、`SBI-123-2` |
| 大きいときの部下のセッション | `SBI-123-1`（任せた行の番号をそのまま名前にする） |
| PR のタイトル・【完了】の1行目 | `SBI-123: <名前>`、`【完了】SBI-123 をマージしました` |
| 統括と部のセッション名 | `Manager-main`・`Req-main`・`Harness-main`・`Test-main`・`Dev-main` |
| 部の仕事の番号 | `REQ-1`・`HAR-1`・`TST-1`・`DEV-1`（子の行は `REQ-1-1`）。PR のタイトルは `REQ-1: <名前>` |
| 統括が自分でやる仕事の番号 | `MGR-1`（子の行は `MGR-1-1`） |

- 番号は 001 からの通し番号で、Issue の番号とは別に持つ（Issue を立てる前に番号が決まり、別の課題管理の道具で番号を振るチームにも合わせられる）。Issue は行の最後の `#番号` で別に持つ
- 番号は、要求分析部が人に確かめてから振る。作業の台帳（作業単位ごとの作業計画の一覧）に書き、次の番号は台帳の最大の次。台帳の場所は、導入したリポジトリの値（`.claude/teamkit.md`）
- **SBI はラインが持つ縦の仕事に限る**。部はリポジトリを横断する関心事を整える役割なので、部の仕事は SBI にしない。SBI-xxx とその子の行は、そのライン（S<番号>-main）が持つ
- **部の仕事は、部ごとの番号で数える**: `REQ-1`（Req-main）・`HAR-1`（Harness-main）・`TST-1`（Test-main）・`DEV-1`（Dev-main）。1からの通し番号で、部ごとに別。子の行は SBI と同じに `REQ-1-1`。番号の頭がそのまま持ち手を表す（一覧に持ち手の列は要らない）。前提はどの番号でも引ける（`（前提: REQ-1, SBI-041-1）`）
- **統括が自分でやる仕事は `MGR-1`**: 1からの通し番号で、統括が自分で振る（台帳に載せず、人にも確かめない。小さな仕事のため）。ほかの持ち手に任せる仕事は、SBI か部の番号にする
- **短い形**（図の丸の下と一覧）: 頭の語の1文字目と残り（`SBI-041-2` → `S041-2`、`REQ-2` → `R2`、`HAR-1` → `H1`、`MGR-1` → `M1`）。全文はツールチップ
- **SBI は粗い粒度にする**（例「会員機能を作る」）。仕事が増えたら、まず既存の SBI の子の行に入れ、SBI を新しく切る・分けるときは先に人に確かめる（細かく切ると、ラインと台帳の節が増えて見通しが悪くなる）
- **地図の Issue**: 台帳に載らない仕事（例 リファクタリング）を、GitHub の Issue 1つを地図にし、サブ Issue を紐づけて1つずつ進めることがある。これも同じ型で扱う
  - 地図の Issue は SBI に当たる（ラインが持つ縦の仕事）。作業計画の置き場は、台帳の節ではなく、その Issue の本文
  - 番号は `I-<Issue の番号>`（0 で埋めない。`#3` と同じ数字で照らせるように）、子の行は `I-3-1`。ラインのセッション名は `I3-main`、置き場所は `.worktrees/I3`、ブランチは `I-3`。短い形は `I3`・`I3-1`
  - 子の行がサブ Issue になるときは、行の終わりの Issue の欄にサブ Issue の番号を書く（`- [ ] I-3-1 部品を分ける #4`）
  - 前提には行の番号（`I-3-2`）を書くのを基本にする（番号の形で、どの持ち手の行か分かる）。サブ Issue の `#番号` でも引け、そのときの持ち手は、その `#番号` を行の終わりに持つ行の持ち手
  - 状態は TASK.md の行（印と済んだ日）だけで持つ。Issue のチェックボックスやサブ Issue の開閉とは二重に管理しない（道具は GitHub を読まない）
  - 立てるのは要求分析部。人と要求を詰めた結果として、SBI と同じく先に人に確かめてから立てる。開発推進部が受け付けたふつうの Issue は統括が振り、大きくて切り分けが要るものだけを統括が要求分析部に回す

## 4. スプリントの区切り

仕事はスプリントで区切る。区切りは根の持ち手（統括）が受け持つ（誰に任せるかは `roles.md`）。

- **スプリントの間**: 済んだ行も `[x]` のまま消さない（済んだ枝も、束から開いて見られるように）。部下の置き場所も片付けない
- **スプリントの終わりに写す**: 全部の TASK.md を、木ごと写しの置き場へ写す。写しの置き場は git の外で、場所は導入したリポジトリの値の「写しの置き場」。スプリントごとに1つのフォルダを作り、その中に、根の TASK.md と束のフォルダの相対の位置を保ったまま全文を写す（申し送りの節も含む）。写したフォルダを道具に渡すと、そのスプリントの全体像と図が出る（`views.md` の1章）
- **写したあとに片付ける**: 済んだ行（`[x]` の行と、枝が全部済んだ束）を消し、部下の置き場所を片付ける。片付けるのは持ち手が止まっているときで、申し送りの節には触れない
- **未完の行**: 番号を変えずに残す。次のスプリントの計画で、並びと着手予定日を引き直し、要らなければ消す（番号が変わらないので、前提が外れない）
- **目標を閉じるとき**: 統括の目標を切り替えるときも、同じ写しの置き場に写す

## 5. 道具が守ること

- 部品とスキルは TASK.md を読むだけで、書き換えない。書くのは持ち主のセッションだけ（例外は、4章のスプリントの終わりの片付け）
- GitHub を読まない（Issue の番号は文字として引くだけ）
- 束をたどる深さは3段（統括 → 部・ライン → 部下）
- 末尾の申し送りの節と `## メモ` の節は、全体像に出さない

## 6. 採らなかった案と理由

- 語を設定ファイルで変える（少しだけ・広く）: 型が2つに見え始め、道具と説明が重くなる。足りなければ使いながら足す
- 番号の形を決まった接頭辞（`SBI-` など）だけにする: 別の接頭辞を使うチームで、道具を直すことになる
- 作業単位の番号を Issue の番号に揃える（SBI-207 ＝ Issue 207）: 番号は1つで済むが、Issue を立てるまで番号が決まらず、別の課題管理の道具で番号を振るチームに合わない
- 番号のない行を、前提に行の名前で書いて引く: 行の文面を直すと前提が黙って外れる（または人の作業に変わる）
- 番号のない行を許し、短い形を持ち手の頭の字と通し番号にする: 番号の短い形とぶつかる（`REQ-1` も Req-main の番号のない1行目も `R1`）。番号のない行の頭を小文字にして見分ける: 管理の外の行に見分けを足すより、管理する仕事に番号を付ける方が簡単
- 子の行の番号を待たれる行だけにする: 待たれると分かったときに後から付ける手間。道具が並びで自動に振る: 行を入れ替えると番号が変わり、前提が黙って別の行を指す
- ラインのセッション名を番号そのまま（`SBI-123`）にする: 番号1つで全部が引けるが、統括と部のセッション名（〜-main）と形がそろわない
- 束を、子の TASK.md の全部を指す参照にする: 依頼を入れ替える持ち手では、同じ置き場所を指す束が並び、どの束の中身か食い違う。子の TASK.md が次の依頼に書き換わると、済んだ依頼の中身が残らない
- 依頼ごとに TASK.md を分ける（1依頼 ＝ 1ノード）: 1つの持ち手が複数のノードを持つので、帯と空きを持ち手ごとに集め直し、申し送りの置き場所も決め直すことになる。スプリントの区切りで写すなら、枝で表すのと差が小さい
- 階層をやめ、全部の行を1枚の一覧にする: 複数のセッションが同じファイルを書いてぶつかり、各セッションが全部を読むことになる
- 部も依頼ごとにセッションを閉じる: 部が長く持つ前提（持ち場の知識、申し送り）が崩れ、立て直しの手間が毎回かかる
- 子の TASK.md の、どの束にも当たらない行を、親の全体像に「そのほか」で出す: 束のない仕事を許すことになり、親が知らない仕事が増える
- 進行中を、持ち手のセッションが動いているかで決める: 手を付けた仕事でも、セッションが止まっていると未着手に見える
- 進行中を、行があるかで決める（着手するときに初めて行を書く）: 行を足しておき、着手はスプリントの後半、という書き方がふつうにある
- 束にも任せた側が印（`[/]`・`[x]`）を書く: 親と子で同じ状態を2か所に書き、食い違う
- 書いた前提だけを待ちにし、順番は見せるだけにする: ラインの行が全部「始められる」に出て、どれがブロッカーか分からない。束も順番に入れる: 統括の並行するラインどうしまで直列の待ちになる
- 完了の予定も持つ: 着手の予定と済んだ日で、並びと遅れは把握できる。着手した日も手で書く: 書き忘れが増える（着手は `[/]` で分かる）。道具が状態の変わり目を記録して着手日を出す: 記録する道具のない環境で出ない
- 予定を引き直したとき最初の予定も残す・年も書く: 行が長くなる
- 前倒し・遅れの印を全体像・図・計画に出す、図の横軸を日付にする: 見る所が増えて読みにくくなる。人が日付を見れば足りる
- 統括が子の行の日付まで全部書く: 持ち主だけが TASK.md を書く決まりとぶつかる
- 説明を行の中に区切り（`｜` など）で書く: ファイルの中では行が長いまま。名前・説明・前提・日付・束を全部字下げの項目に分ける: 行が長くなり、前提や束を読むのに行の下まで見ることになる。説明を持たず Issue だけに書く: Issue を立てない小さな仕事で、何をするかがどこにも残らない
- 写しを Issue に貼る: 区切りごとに全部の持ち手の分を貼ると重く、写しを道具で読めない

## 7. 使いながら確かめること

- 順番を暗黙の前提にしたことで、並べて進められる行まで待ちに見えて困らないか（困るなら部下に任せる書き方で足りるか）
- 番号の形が広いので、行の先頭の語（`UTF-8` など）を番号と読んで困ることがないか
- `[/]` の書き忘れ（とくに取りかかった直後）と、`[x]` のときの済んだ日の書き忘れ。年をまたぐときの読み方。前倒し・遅れの印がなくて困らないか
- スプリントの終わりまで済んだ行を残すことで、TASK.md が長くなりすぎないか
- 小さな仕事にも番号を付けることが、手間になりすぎないか
- 名前の 20字の目安が、短すぎて何の仕事か分からなくならないか。道具が数えずに守られるか
